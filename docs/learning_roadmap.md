# Learning Roadmap

This project should not wait for a perfect heuristic bot before adding learning. The current path is a hybrid:

1. Heuristics remain the safety controller.
2. JSONL logs provide training data.
3. Learned models score low-risk decisions in shadow mode first.
4. Rules keep veto power until offline replay and live probes show improvement.

## Current Status

- `slay_ai.learn` can replay completed runs into `data/learned_memory.json`.
- `slay_ai.train_card_model` can train `models/card_value_model.json`.
- `slay_ai.train_deck_quality_model` can train a shadow-only `models/deck_quality_model.json` from `pre_boss_deck_quality` rows; it is not wired into policy control.

## Project Phases

- Stage 1: engineering loop / automatic operation is complete.
- Stage 2: heuristic strategy prototype is complete.
- Stage 3: log learning / lightweight model is initially complete.
- Stage 4: search planning / deck evaluation is in progress. A conservative one-turn combat local search prototype exists, but broader deck evaluation and calibrated search scoring are not complete.
- Stage 5: autonomous learning AI is not complete; any learned model should remain shadow scoring, tie-breaker, or high-confidence veto only.
- Stage 6: high-win-rate A20 validation is not complete. Current work must still follow the real unlock frontier, not claim A20 until unlocked and proven.

## Agent Consensus

The current advisory agents agree on this boundary:

- Start learning now, but only as an assistant to the heuristic policy.
- Do not let a model control the whole run yet.
- Begin with card rewards because the action space is small and the logs already capture candidate cards.
- The next autonomous-learning surfaces should be shadow scoring for route risk, potion tempo, shop buying, and rest/smith thresholds.
- Use stable ids for features and labels: card ids, relic ids, potion ids, screen types, and commands.
- Keep full combat learning for later; first improve combat with rules, one-turn local search, and encounter-specific evidence.
- Do not expand learning authority while execution-layer logs are polluted by MCP/action races; fix and exclude diagnostic runs first.
- After probe64, the next Stage 4 milestone is Slime Boss split/minion planning: split timing, post-split multi-target pressure, Slimed hand pollution, defensive floor, and potion/AoE tempo. This should be implemented as search/evaluator improvements before any broad learned combat controller.

`slay_ai.offline_batch` is the preferred read-only replay entry point for completed logs. It writes a manifest, shadow rows, shadow advice, per-run diagnosis JSON, Act 1 boss gate, a compact batch summary, and per-agent handoff files under `handoff_<name>/<agent>.json` plus matching `handoff_<name>/<agent>.txt` prompt files, without touching live MCP or training new models. It also writes `handoff_<name>/index.json` and `handoff_<name>/next_handoff.txt`, so the coordinator can open one file to find the primary worker prompt and the main-agent merge prompt; `next_handoff.txt` starts with a `Handoff summary` containing primary/coordinator selections, the Act 1 boss gate status line, gate remaining progress, latest-run acceptance, next probe goal, `agent_queue_counts`, compact `agent_queue_actions`, classification reasons, and gate failure evidence before the full prompts. The top-level `artifact_manifest_<name>.json` records existence, size, and sha256 for input paths, resolved JSONL logs, and generated files plus directory counts for output folders, so worker agents can treat missing or corrupt source/handoff paths as infrastructure issues instead of strategy evidence. Empty directory inputs add a `no_resolved_logs` warning while leaving file health separate from evidence sufficiency. Per-run diagnosis filters advice rows by `source_log`, so one run does not inherit another run's shadow-model warnings inside a batch. The summary mirrors gate pass/status/action, progress, remaining progress, next probe goal, latest-run acceptance, and the recommended next action at top level for simple monitors, and the CLI prints the same fast handoff entry as an `offline_batch_next:` line with recommended action, primary/coordinator tasks, live-MCP ownership requirements, and queue counts; it also includes `batch_triage`, which rolls up classification counts, artifact paths, per-run handoff actions, failure attributions, manifest-level failure evidence, label quality, gate status, gate progress and remaining progress, shadow-advice provenance, the gate's `next_probe_goal` / `latest_run_acceptance`, gate-level `execution_recovery`, gate-level data quality, gate-level failure evidence, and runner/engineering/AI/main-agent queues. Runner queue items carry the gate acceptance criteria directly for passed gates and unmet collection goals, so the flow agent can collect the next validation batch or missing pristine boss evidence from the summary alone. AI queue items also carry gate-level route or boss-combat improvement goals when the Act 1 boss gate fails before the collection phase, plus a `review_gate_data_quality` task when gate-level feature coverage gaps, feature-zero rows, missing coverage, or label exclusions need an offline shadow-data audit. Main-agent queue items carry the same gate context, including `gate_failure_evidence`, so the coordinator can merge or override work without reopening the gate report. Every queue item and each per-agent handoff file carries artifact paths for the manifest, shadow rows, advice, diagnosis, gate, summary, and artifact manifest when those artifacts exist; per-run queue items also carry compact shadow-advice provenance so an AI worker can audit advice inputs plus model source/load quality without opening the full advice directory first. Each handoff file also includes its own path, the full `agent_handoff_paths` / `agent_prompt_paths` indexes, an `ownership_contract` describing the agent's lane and live-MCP boundary, per-task `execution_contract` metadata so a worker can tell whether a task is offline-only or requires explicit live-MCP ownership, `offline_refresh_command.argv` for replaying the original input paths, `offline_refresh_command.resolved_argv` for replaying the exact resolved JSONL set when available, and an `assignment_prompt` that can be sent directly to the worker without re-explaining scope. Assignment prompts include first-task counts, queue length and queued actions when multiple tasks exist, source paths, acceptance criteria, gate remaining progress, latest-run acceptance, next probe goal, the Act 1 boss gate status line, shadow-advice provenance, shadow label quality, manifest-level recovery counters, gate execution recovery, gate data quality, gate failure evidence, and the artifact-manifest path when those fields exist. `agent_queue_counts`, `agent_queue_actions`, and `next_handoff` give the coordinator a fast view of queue size, queued actions, execution mode, live-MCP ownership requirements, gate metric/deficit and latest-run blockers for gate-owned tasks, the first worker task, and the main-agent merge task. Agent queues prefer the strongest per-run diagnosis action and keep coarser manifest failure attributions as statistics, so a missed-lethal diagnosis can override a broader potion-planning bucket for handoff. Use the lower-level commands below it when you need to retrain models, compare advice directories, or inspect a single artifact.

The manifest is the gate between execution evidence and learning. Completed clean failures are trainable; action failures, unrecovered action races, MCP read failures, and manual diagnostics stay visible but out of default training. The manifest records both `inputs` and `resolved_logs`, plus their counts in `summary`, so standalone training manifests can be traced back to the exact JSONL files used for classification; if no logs resolve, it records `no_resolved_logs` in `warnings`. The `failure_attribution` field is diagnostic metadata, not a label override: it helps decide whether a failed clean run should feed card/deck, route, potion, combat-planning, or MCP-execution analysis.
The manifest summary also includes `classification_reasons` per bucket, `failure_evidence` rollups by evidence type, reward/chest screen-stall screen/reason, action-error kind/status, MCP read event/status, and synthetic-terminal source, plus `action_recovery` and `terminal_recovery` counters. `act1_boss_gate` and `offline_batch` carry the same distributions into gate reports, batch triage, agent handoff indexes, and worker assignment prompts; the gate CLI status line includes compact top failure-evidence, screen-stall, action-error, MCP-read, and terminal-source suffixes when present. `act1_boss_gate` also aggregates recovery counters under `execution_recovery`, with compact status-line suffixes for top action-recovery kind and terminal-recovery outcomes. Use these fields to tell whether an infra-heavy batch is mostly MCP null/read failures, stale target/potion/action races, terminal-recovery instability, or reward/chest screen stalls before assigning runner, engineering, or AI work.
The static knowledge directory adds compact factual features such as `deck_tag_aoe`, `deck_tag_weak`, `potion_role_emergency`, `enemy_boss_count`, and `enemy_max_expected_attack`; these features help shadow models reason about Act 1 readiness without treating wiki/mod data as outcomes.

`training_manifest` also writes validation metadata that is separate from training eligibility. `validation_grade=pristine` is the strict gate for boss-stability claims; `usable_with_recoveries` and `diagnostic` can still preserve evidence such as `act1_boss.reached` or `act1_boss.cleared`, but they should not be counted as pristine validation. `summary.validation` rolls up grades, validation flags, Act 1 boss prefix blockers, and non-pristine boss-clear blockers; `offline_batch` carries that summary into handoff JSON and worker prompts so agents can see why evidence does or does not count toward the A0 boss gate.

The lightweight shadow trainers use the same gate. `train_route_risk_model`, `train_potion_tempo_model`, `train_deck_quality_model`, `train_combat_search_model`, and `train_shadow_models` default to `--source-quality pristine`. Use `--source-quality usable` only for explicit recovered-race diagnostics or ablations, and `--source-quality legacy` only when intentionally reusing old ungraded shadow files. Shadow model files now record category-level `metadata.training_source`, and `train_shadow_models` writes a top-level `shadow_training_source`, so route/potion/deck/combat models can be traced back to the exact shadow JSONL files and source-quality gate used for training. `shadow_advice` rows now carry their `shadow_source_file` when scored from JSONL files, or `in_memory_examples` when produced inside runner, and `summary.json` rolls up both shadow inputs and model training sources. `run_diagnosis` preserves that provenance in its `shadow_advice` block so agent handoffs can audit advice inputs without reopening the advice directory.

`train_card_model` also records model provenance in `metadata.training_source`: raw directory/file inputs are marked `ungated_logs`, while `--manifest` records the manifest path, clean_trainable paths, resolved JSONL logs, missing clean paths, and warnings under `clean_trainable`. `slay_ai.learn` uses the same source resolver and writes `last_learning_replay` plus `learning_replays` into learned memory with the source, read/applied/skipped counts, and warnings.
